# AGENTS.md

Правила работы над проектом Word Formatter для ИИ-агентов и разработчиков.
Если задача противоречит этому файлу — сначала обсудите противоречие,
потом меняйте код.

## 1. Что это за проект

Настольное приложение (Windows и Linux), которое приводит документ Word
к требованиям профиля оформления. Стек: Python 3.10+, `python-docx`,
`lxml`, `PySide6-Essentials`, `pytest`.

Документы проекта, которые нужно прочитать перед изменениями:

- [docs/SPEC.md](docs/SPEC.md) — что входит в MVP и критерии готовности;
- [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) — устройство и принятые решения;
- [docs/PROFILES.md](docs/PROFILES.md) — формат профиля оформления;
- [PROJECT_STRUCTURE.md](PROJECT_STRUCTURE.md) — назначение папок;
- [README.md](README.md) — то, что читает пользователь.

## 2. Главные правила проекта

1. **Содержание важнее оформления.** Приложение меняет только оформление.
   Любая правка, которая может изменить текст, порядок абзацев, таблицы,
   изображения, сноски, поля или объекты, требует отдельного обоснования
   и проверки сохранности.
2. **Исходный файл не изменяется никогда.** Открытие — только для чтения,
   запись — только в отдельный файл через временный файл.
3. **Не угадывать.** Если признаков не хватает, абзац получает роль
   «спорный»: оформление не меняется, случай попадает в отчёт. Это лучше,
   чем испортить документ.
4. **Профиль — это данные, а не код.** Добавление профиля не должно требовать
   изменения алгоритма. Если для нового профиля нужен код — значит,
   архитектура выбрана неверно; обсудите это.
5. **Проверка сохранности обязательна.** После сохранения результат
   сравнивается с исходником (`core/verification.py`). Не отключайте эту
   проверку и не ослабляйте её условия без обоснования.
6. **Текст для пользователя — на русском и понятный.** Ошибка должна
   объяснять, что случилось и что делать. Технические подробности идут
   в поле `details` и в журнал, а не в лицо пользователю.
7. **Порядок элементов меняется только у подписей.** Единственная разрешённая
   перестановка — перенос подписи рисунка или названия таблицы туда, где
   требует профиль (`captions.*.position`). Любая другая перестановка абзацев
   запрещена. После переноса правило свободных строк обязано работать
   с пересобранной картиной документа (`inspect_document`), а проверка
   сохранности получает число разрешённых переносов (`expected_moves`).

## 3. Работа с кодом

- Ядро `word_formatter/core/` **не импортирует** `word_formatter/ui/`.
  Логика обязана тестироваться без графики.
- Порядок элементов OOXML строго задан схемой. Новые свойства оформления
  добавляйте через `ensure_ordered_child` с таблицей порядка
  (`core/rules/xml_helpers.py`), а не через `append`.
- Ссылки на шрифт темы (`w:asciiTheme` и подобные) и конкурирующие настройки
  (`w:firstLineChars`, `w:hanging`, `w:beforeAutospacing`) нужно снимать:
  иначе Word покажет старое оформление.
- Прогоны без текста (`w:t`) не трогайте: в них сноски, поля и разрывы.
- Новое правило оформления: отдельный модуль в `core/rules/`, вызов
  в `core/rules/runner.py` в правильном месте порядка, запись изменений
  в `context.changes`.
- Новый элемент документа: роль в `Role`, признак в `core/docx/inspection.py`,
  тест на распознавание и тест на случай, когда приложение обязано отказаться
  от догадки.
- Не добавляйте зависимость без необходимости. Текущий набор минимален
  и обоснован в README.

## 4. Скрипты запуска

- `run_windows.bat` содержит **только латинские символы, включая
  комментарии**: cmd.exe разбирает пакетные файлы по текущей кодовой странице
  и выполняет части русских слов как команды. Русский текст лежит
  в `tools/messages/*.txt` и печатается командой `type` после `chcp 65001`.
  На это есть тесты — не отключайте их.
- `run_linux.sh` должен иметь переносы строк LF и начинаться со строки
  `#!/usr/bin/env bash`. Файл обязан остаться пригодным для запуска
  через `bash run_linux.sh`, даже если право на исполнение не выставлено.
- Логика подготовки окружения живёт в `tools/bootstrap.py`, а не в скриптах.
- Ничего не устанавливается глобально, права администратора не требуются,
  системные настройки не меняются, пользовательские файлы не удаляются.

## 5. Команды

```bash
# окружение разработчика
python -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt   # Windows: .venv\Scripts\python.exe

# тесты
.venv/bin/python -m pytest

# только быстрые тесты логики
.venv/bin/python -m pytest tests/unit

# проверочные команды приложения
.venv/bin/python main.py --version
.venv/bin/python main.py --list-profiles

# подготовка окружения без запуска (то же, что делают скрипты)
python tools/bootstrap.py --setup-only
```

Тесты графического интерфейса идут в невидимом режиме
(`QT_QPA_PLATFORM=offscreen`); этот режим выставляется в `tests/conftest.py`.

## 6. Определение готовности задачи

Задача считается выполненной, когда:

1. выполнены требования и критерии приёмки из `docs/SPEC.md`, относящиеся
   к задаче;
2. запущены тесты, и их результат указан в отчёте (без придуманных результатов);
3. новый код покрыт тестами: отдельными на поведение и общим контрактом
   «меняется только оформление» (`tests/integration/test_apply_contract.py`);
4. обновлены документы, если изменились поведение, формат профиля или
   структура проекта;
5. в отчёте отделены фактические проверки от предложений;
6. в изменениях нет секретов и посторонних файлов.

## 7. Git

- Коммиты — по-русски в стиле Conventional Commits: `feat:`, `fix:`, `docs:`,
  `test:`, `refactor:`, `chore:`.
- Не выполняйте `push`, публикацию релизов и слияние веток без отдельного
  разрешения.
- Не добавляйте в репозиторий `.venv`, кэши, журналы и локальные профили:
  они перечислены в `.gitignore`.
- Перед коммитом проверьте `git status` и `git diff`, чтобы в него не попали
  посторонние изменения.
- Чтобы `run_linux.sh` был исполняемым в репозитории, выставите право
  отдельно: `git update-index --chmod=+x run_linux.sh`.

## 8. Чего не делать

- Не переписывать текст документа (в том числе не менять регистр букв
  в тексте: прописные включаются оформлением `w:caps`).
- Не удалять и не пересоздавать части пакета DOCX: сноски, комментарии,
  объекты OLE и пользовательский XML переносятся как есть.
- Не заявлять о проверках, которые не запускались.
- Не публиковать профили, выдавая непроверенные параметры за требования
  методички: у каждого профиля должен быть указан источник.
