Этот документ описывает **фактическое** состояние проекта.

## Назначение каталогов

| Каталог | Назначение |
|---|---|
| `word_formatter/core/` | Вся логика работы с документами и профилями. Не импортирует графический интерфейс |
| `word_formatter/core/profiles/` | Модель профиля, проверка файла, каталог встроенных и личных профилей |
| `word_formatter/core/docx/` | Открытие документа, определение роли абзацев, инвентарь элементов |
| `word_formatter/core/rules/` | По одному модулю на категорию оформления; `runner.py` задаёт порядок |
| `word_formatter/ui/` | Только интерфейс: окно, диалоги, фоновый поток |
| `profiles/` | Встроенные профили оформления (данные, а не код) |
| `examples/` | Пример документа, результат его обработки, отчёт и предпросмотр |
| `tools/` | Вспомогательные скрипты для запуска и сборки примера; `messages/` — русские тексты для `.bat` |
| `docs/` | Документация для разработчика и заказчика |
| `tests/unit/` | Быстрые тесты логики без обращения к настоящим файлам Word |
| `tests/integration/` | Тесты на эталонном документе, полном проходе и интерфейсе |

## Корневые файлы

| Файл | Назначение |
|---|---|
| `main.py` | Точка входа. Содержит только вызов `word_formatter.app.main()` |
| `run_windows.bat` | Поиск Python и передача управления `tools/bootstrap.py`. Только ASCII |
| `run_linux.sh` | То же для Linux. UTF-8, переносы строк LF |
| `requirements.txt` | Рабочие зависимости с точными версиями |
| `requirements-dev.txt` | Дополнительно `pytest` и `pytest-qt` |
| `pytest.ini` | Каталог тестов по умолчанию |
| `README.md` | Что делает приложение, как запустить, что делать при ошибках |
| `AGENTS.md` | Правила работы над проектом: что можно и чего нельзя |
| `PROJECT_STRUCTURE.md` | Этот файл: назначение папок и правила размещения |

## Правила размещения

1. Логика — в `word_formatter/core/`, интерфейс — в `word_formatter/ui/`.
   Логика не должна зависеть от интерфейса.
2. Новое правило оформления — отдельный модуль в `core/rules/` и вызов
   в `core/rules/runner.py` в правильном месте порядка.
3. Профили оформления — только данные: `profiles/` для встроенных,
   личная папка пользователя для своих. Код при этом не меняется.
4. Тесты логики — в `tests/unit/`, тесты на настоящих документах — в
   `tests/integration/`. Эталонный документ собирается кодом
   (`tests/fixtures/rich_docx.py`), а не хранится готовым файлом: так видно,
   что именно в нём есть.
5. Новые документы — в `docs/`. README не дублирует `docs/SPEC.md`
   и `docs/ARCHITECTURE.md`: он для пользователя.
6. Не создавать новые каталоги верхнего уровня без необходимости.
7. Не помещать в репозиторий `.venv`, журналы, локальные профили
   и результаты обработки: они перечислены в `.gitignore`.

## Поддержание документации

При изменении структуры проекта:

- обновите дерево и таблицы в этом файле;
- проверьте, не устарели ли команды в `README.md` и `AGENTS.md`;
- если изменился формат профиля — обновите `docs/PROFILES.md`;
- если изменилось поведение приложения — обновите `docs/ARCHITECTURE.md`
  и, при необходимости, `docs/SPEC.md`.

Документация должна описывать фактическое состояние проекта и не утверждать,
что ещё не реализованные части уже существуют.
