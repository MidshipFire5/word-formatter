## Сценарии

### 1. Приложение запускается через main.py — проверено

- `python main.py --version` → `Word Formatter 0.1.0`.
- `python main.py --list-profiles` → список профилей и пути к папкам.
- Реальный запуск графического интерфейса: процесс `main.py` поднялся,
  работал, при завершении не оставил следов в системе; журнал создан.
- Тесты: `tests/unit/test_cli.py`.

### 2. Приложение запускается через run_windows.bat — проверено

Реальный запуск скрипта: он нашёл Python, вызвал `tools/bootstrap.py`,
убедился, что окружение готово, и запустил приложение **Python из `.venv`**:

```
.venv\Scripts\python.exe ...\main.py
```

Приложение работало, журнал записан. Скрипт корректно возвращает код
завершения и делает паузу при ошибке, чтобы пользователь успел прочитать текст.

### 3. Приложение запускается через run_linux.sh — требует проверки заказчиком

Локально проверить нельзя: рабочая машина — Windows. Что сделано:

- скрипт проверен на соответствие требованиям Linux: переносы строк LF,
  строка `#!/usr/bin/env bash`, запасной способ `bash run_linux.sh`,
  подсказки по установке Python и системных библиотек (тесты
  `tests/unit/test_run_scripts.py`);
- в непрерывной интеграции есть отдельная задача «Первый запуск через скрипт
  (Ubuntu)», которая выполняет `bash run_linux.sh --setup-only`, проверяет
  работу приложения из созданного окружения и то, что повторный запуск
  не переустанавливает зависимости.

Фактический запуск в Linux нужно выполнить на Linux-машине (см. README,
раздел «Запуск в Linux») и сообщить результат.

### 4. Первоначальная настройка окружения — проверено

- Полный проход: удалена отметка об установке → `tools/bootstrap.py --setup-only`

  `.installed-requirements` и `.qt-platform-ok`, код завершения 0.
- Создание окружения с нуля проверяется в CI на Ubuntu.
- Тесты: `tests/unit/test_bootstrap.py`.

## Что дала приёмка

Визуальная проверка отрендеренного результата нашла **три дефекта**, которых
не видели автотесты на синтетическом документе. Все исправлены и закрыты
тестами:

1. **Заголовки получались синими.** Приложение назначает абзацам встроенные
   стили Word, а они по умолчанию окрашены (Heading 1 — `365F91`,
   Heading 2 — `4F81BD`). Профиль цвет не задаёт, поэтому синий цвет
   просачивался в результат. Теперь определения стилей, которые задаёт
   профиль, описываются полностью: если цвет не указан, ставится «авто».
2. **Строка содержания принималась за заголовок.** «1 Теоретические основы
   ………… 4» распознавалась как заголовок раздела и получала стиль и
   полужирный. Добавлен признак отточия: такие строки — обычный текст.
3. **Титульный лист переформатировался как основной текст** — терялось
   центрирование. Методичка оформление титульного листа не задаёт, поэтому
   теперь абзацы до первой структурной части **остаются как были**, а в отчёт
   попадает пункт «Титульный лист оставлен без изменений».

Для воспроизведения этих случаев добавлен пример документа
(`tools/make_example.py` → `examples/пример-курсовой.docx`) и тест
`tests/integration/test_example_document.py`, который проверяет результат
обработки именно на нём.

## Проверка в среде с ограничениями (найдено при приёмке)

При запуске приложения из рабочей папки DSH сохранение в «Загрузки» отклоняется
системой с сообщением «У вас нет разрешения на сохранение файлов в этом месте».

**Это не ошибка приложения.** Проверено и воспроизведено:

| Где находится Python приложения | Запись в «Загрузки» |
|---|---|
| `…\DeepSeekHarness\01 - Projects\Word Formatter\.venv` | запрещена |
| `…\DeepSeekHarness\01 - Projects\_wf-venv-test` | запрещена |
| `A:\YandexDisk\YandexDisk\_wf-venv-test` | разрешена |
| `A:\wf-venv-test` | разрешена |
| `C:\wf-venv-test` | разрешена |

Дополнительно установлено:

- права на папку «Загрузки» обычные: владелец имеет полный доступ;
- защита от программ-вымогателей (Controlled Folder Access) выключена;
- системный Python (`C:\Users\…\Python311\python.exe`) пишет в «Загрузки» без
  проблем — то есть дело не в самой системе и не в папке;
- процесс, запущенный службой Windows (вне цепочки процессов DSH), тоже
  ограничен, если интерпретатор лежит внутри папки `DeepSeekHarness`.

Вывод: среда DSH ограничивает запись процессами, запущенными из своей рабочей
папки, — независимо от того, кто именно их запустил. Приложение работает
правильно; ограничение снимается, если разместить проект вне папки
`DeepSeekHarness` (или запускать его вне этой среды).

В README добавлена строка разбора этой ошибки для пользователя.

## Оставшиеся ограничения

Сознательные ограничения первой версии (описаны в README и отчёте приложения):

- формулы и встроенные объекты не переоформляются, только сообщаются;
- автоматическое содержание не пересчитывается: поле помечается для обновления;
- запрет переноса внутри сокращений и чисел Word не поддерживает настройкой;
- маркеры списков не заменяются на тире;
- старый формат `.doc` и документы с макросами `.docm` не поддерживаются;
- абзацы внутри элементов управления содержимым (готовые блоки Word)
  в разбор не попадают.

Не проверено:

- фактический запуск в Linux (см. сценарий 3);
- работа с документами, созданными не Microsoft Word (например, LibreOffice
  или Google Документы) — проверялось открытие результата, но не обработка
  таких исходников;
- документы большого объёма (сотни страниц): время обработки не измерялось.
