# Устройство приложения

Документ объясняет, из чего состоит приложение, как проходит обработка
документа и почему приняты те или иные решения. Он рассчитан на разработчика,
который будет менять код.

## Слои

```
main.py                     точка входа, ничего кроме вызова app.main()
word_formatter/app.py       разбор аргументов командной строки, запуск интерфейса
word_formatter/ui/          PySide6: окно, фоновый поток, диалоги
word_formatter/core/        вся логика; ничего не знает про интерфейс
tools/bootstrap.py          подготовка окружения и запуск (до появления Python-зависимостей)
profiles/                   встроенные профили оформления
tools/messages/             русские тексты сообщений для скриптов запуска
```

Главное правило: **`core` не импортирует `ui`**. Благодаря этому вся логика
форматирования проверяется тестами без графики — быстро и без экрана.

## Модули ядра

| Модуль | Ответственность |
|---|---|
| `core/errors.py` | Ошибки с готовым текстом для пользователя |
| `core/paths.py` | Встроенные профили, личная папка пользователя, журналы |
| `core/profiles/model.py` | Неизменяемая модель профиля (dataclass) |
| `core/profiles/validation.py` | Проверка файла профиля с русскими сообщениями |
| `core/profiles/loader.py` | Каталог профилей: встроенные и личные, слияние по `id` |
| `core/docx/opening.py` | Открытие документа с понятными ошибками формата, пароля, повреждения |
| `core/docx/elements.py` | Роли абзацев, инвентарь документа |
| `core/docx/inspection.py` | Определение роли каждого абзаца и состава элементов |
| `core/rules/` | Правила оформления по категориям |
| `core/rules/runner.py` | Порядок применения правил |
| `core/report.py` | Отчёт: что сделано, что проверить, как проверить |
| `core/verification.py` | Сравнение исходника и результата |
| `core/processing.py` | Полный проход: открыть → применить → сохранить → проверить → отчёт |

## Как проходит обработка

```
исходный файл (только чтение)
    → open_document: проверка формата, пароля, повреждения
    → inspect_document: роли абзацев, таблицы, состав элементов
    → apply_all_rules: изменение оформления в памяти
    → сохранение через временный файл рядом с целью
    → verify_files: сравнение исходника и результата
    → build_report: отчёт для пользователя
```

Сохранение идёт через временный файл (`.word-formatter-*.docx` в целевой папке)
с последующим переименованием: неудачное сохранение не оставит обрезанный
документ на месте готового. Сохранение поверх исходного файла запрещено
функцией `ensure_output_is_safe`.

## Порядок применения правил

Порядок в `core/rules/runner.py` важен:

1. параметры страницы;
2. оформление по умолчанию (стиль «Обычный» и `docDefaults`);
3. определения стилей заголовков;
4. переносы (настройка документа);
5. основной текст;
6. перечисления;
7. заголовки (абзацы);
8. подписи;
9. таблицы;
10. сноски;
11. нумерация страниц;
12. **свободные строки — последними**, потому что они добавляют абзацы и
    сдвигают нумерацию: все остальные правила должны отработать до них.

## Ключевые технические решения

### python-docx плюс точечная правка XML

`python-docx` умеет не всё: нет API для переносов, полей, стилей сносок,
положения элементов. Поэтому он используется как основа, а недостающее
дописывается в XML через `lxml`.

Перед началом работы это проверено отдельным тестом (`tests/integration/test_docx_preservation.py`),
и вот что установлено фактически:

- части, которых библиотека не понимает (сноски, изображения, объекты OLE,
  пользовательский XML), переносятся **байт в байт**;
- части, которые она разбирает (текст, стили, настройки, комментарии,
  колонтитулы, свойства), записываются заново с другими отступами, но **состав
  элементов и тексты совпадают**;
- библиотека переписывает `[Content_Types].xml`, заменяя правило по расширению
  правилом для конкретной части; **действующие типы содержимого при этом
  не меняются**.

### Порядок элементов OOXML

Порядок элементов внутри `w:rPr`, `w:pPr` и `w:settings` задан схемой.
Элемент не на своём месте — и Word может отказаться открывать документ.
Поэтому в `core/rules/xml_helpers.py` есть таблицы порядка и функция
`ensure_ordered_child`, которая вставляет элемент на предписанное место.
Тесты проверяют порядок отдельно.

### Ссылки на шрифт темы снимаются

В современных документах Word пишет `<w:rFonts w:asciiTheme="minorHAnsi"/>`.
Атрибуты темы имеют приоритет над явным именем шрифта: пока они на месте,
документ показывает Calibri или Aptos, что бы мы ни задали. Поэтому
`set_rfonts` их удаляет — и в оформлении по умолчанию, и в каждом прогоне.

### Снимаются конкурирующие настройки

`w:firstLineChars` (отступ в символах), `w:hanging` (висячий отступ),
`w:beforeAutospacing` и `w:afterAutospacing` (автоматические интервалы)
перебивают значения, которые задаёт профиль. Они удаляются явно.

### Прогоны без текста не трогаются

Прогон со сноской, полем или разрывом не содержит `w:t`. Если задать ему
шрифт 14 пт, сноска потеряет вид, а поле перестанет работать. Правила
пропускают такие прогоны (проверка `run_has_text`).

### Прописные буквы включаются оформлением

Заголовки структурных частей печатаются прописными, но переписывать текст
нельзя — это уже содержание. Поэтому включается `w:caps`: Word показывает
«ВВЕДЕНИЕ», а в файле текст остаётся таким, каким его набрал автор.

### Роли абзацев и отказ от догадок

`inspection.py` определяет роль каждого абзаца: основной текст, пустая строка,
структурный заголовок, заголовок раздела, элемент перечисления, подпись
рисунка, название таблицы, продолжение таблицы, формула, рисунок, текст
в таблице, спорный абзац.

Уровень заголовка берётся из `w:outlineLvl` — так его понимает сам Word
и его автоматическое содержание; имя стиля («Heading 1» или «Заголовок 1»)
используется как запасной признак.

Если признаки противоречат друг другу (стиль заголовка, но длинный текст
с точкой в конце; номер, но с признаками обычного текста; встроенный объект
вместо формулы), абзац получает роль **«спорный»**: оформление не меняется,
а абзац попадает в отчёт. Это осознанный отказ от угадывания.

### Свободные строки

Свободная строка — это реальный пустой абзац, потому что интервалы между
абзацами заданы нулевыми. Предохранители: не вставлять вторую подряд,
не вставлять в начале и конце документа, перед разрывом страницы, между
частями одного целого (рисунок и его подпись, название таблицы и таблица,
части разорванной таблицы). Правило идемпотентно: повторный прогон ничего
не добавляет.

### Нумерация страниц

Номер — это поле `PAGE`, а не текст: иначе при вставке страницы номер
«застынет». Поле ставится в колонтитул, на первой странице скрывается
настройкой `titlePg` («особый колонтитул первой страницы»). Дополнительно:
снимаются сбросы нумерации (`w:pgNumType/@w:start`), чтобы нумерация была
сквозной, и включается `w:updateFields`, по которому Word обновляет поля
при открытии.

Раздел, который наследует колонтитул предыдущего, **не трогается**: обращение
к его колонтитулу вернуло бы колонтитул первого раздела, и номер
продублировался бы.

### Положение подписей

Методички требуют разного расположения подписей: название таблицы — над
таблицей, подпись рисунка — под рисунком. Если в документе порядок обратный,
правило `core/rules/caption_positions.py` переносит подпись на нужное место.

Это **единственное** правило, которое меняет порядок элементов, поэтому оно:

- включается только самим профилем (`captions.*.position`), по умолчанию
  выключено;
- переносит исключительно подписи: текст, таблицы и рисунки не двигаются;
- переносит подпись только если она стоит вплотную к своему рисунку или
  таблице (пустые абзацы между ними не мешают);
- отказывается действовать, если рядом оказались две подписи, и выносит
  место в отчёт;
- записывает каждое перемещение в журнал изменений.

После переноса картину документа нужно **собрать заново**
(`inspect_document`), иначе правило свободных строк будет работать со старыми
номерами абзацев. Это делает `core/rules/runner.py` сразу после переноса.

Проверка сохранности знает о разрешённых переносах: `verify_files` принимает
`expected_moves`, и если порядок абзацев изменился ровно на столько
перемещений, проверка сообщает об этом как о примечании, а не как о потере
содержания. Изменение порядка **без** заявленных перемещений остаётся
ошибкой.

### Положение рисунков и таблиц

Два правила отвечают за то, чтобы рисунок и таблица не уезжали вправо.

`core/rules/figures.py` задаёт абзацу с рисунком выравнивание из профиля
(по умолчанию по центру) и **снимает абзацный отступ**. Одного выравнивания
мало: абзац с картинкой обычно не имеет собственных свойств и наследует
отступ первой строки от стиля «Обычный», которому правило основного текста
задаёт 1,25 см, — рисунок смещается вправо на эту величину. Отступ снимается
явно (`w:ind` с нулями, висячий отступ и «символьные» настройки удаляются).

`core/rules/table_geometry.py` приводит положение таблицы к требованиям
профиля: снимает заданную ширину (`w:tblW` со значением `auto` — это
галочка «Ширина» в свойствах таблицы) и убирает отступ от левого поля
(`w:tblInd`). Заодно удаляются лишние элементы ширины: Word иногда сохраняет
их два, и тогда неизвестно, какое значение настоящее.

Оба правила работают только с положением элемента, не касаясь содержимого.



После сохранения результат открывается заново и сравнивается с исходником
по одиннадцати характеристикам: текст, текст таблиц, изображения,
гиперссылки, сноски, концевые сноски, разделы, поля, встроенные объекты,
элементы управления содержимым, число таблиц.

Добавленные пустые абзацы потерей содержания не считаются, но о них
сообщается числом. Результат проверки попадает в отчёт.

### Скрипты запуска только на ASCII

cmd.exe разбирает пакетные файлы по текущей кодовой странице и портит русские
буквы: части слов начинают выполняться как команды. Поэтому `run_windows.bat`
содержит только латинские символы, включая комментарии, а русский текст
лежит в `tools/messages/*.txt` и печатается командой `type` после
`chcp 65001` — как данные. Соблюдение проверяется тестом.

Логика подготовки окружения написана на Python (`tools/bootstrap.py`), а не
на языке командной строки: один код для Windows и Linux, и его можно
тестировать обычными тестами.

### Зависимости

`PySide6-Essentials` вместо полного `PySide6`: приложению нужны только
QtWidgets, QtCore и QtGui, а загрузка втрое меньше (73 МБ вместо 250 МБ).

Установка зависимостей выполняется только при изменении `requirements.txt`:
отпечаток файла (SHA-256) хранится рядом с окружением. Проверка запуска
графической библиотеки выполняется один раз, её результат тоже кэшируется.

### Интерфейс и потоки

Обработка идёт в отдельном потоке (`ui/worker.py`), поэтому окно не «зависает».
Этапы передаются обратным вызовом `progress` из `process_document`: точных
долей процента нет, и выдумывать их мы не стали — показывается название
этапа и полоса неопределённого хода.

Внешний вид собран в `ui/theme.py`: цвета, шрифт и таблица стилей Qt.
Приложение запускается со стилем Fusion — он рисует элементы одинаково
в Windows и Linux, поэтому тема выглядит предсказуемо на обеих системах.
Карточки, кнопки, поля и полоса хода работы имеют скруглённые углы.

Рамку самого окна рисует операционная система: в Windows 11 она и так
скруглённая, в Linux зависит от темы рабочего стола. Своя рамка (frameless)
сломала бы перетаскивание и изменение размера, поэтому окно остаётся
обычным. Состояния элементов (обычное, успех, ошибка, перетаскивание файла)
задаются свойством виджета `state`, а `theme.set_state` перерисовывает его.

Документ можно выбрать кнопкой или **перетащить в окно** — при перетаскивании
карточка документа подсвечивается. Так же работает кнопка «Создать профиль
из методички…»: файл методички можно перетащить прямо на неё.

### Профиль из методички

`core/profiles/extraction/` превращает методичку в черновик профиля — то есть
в обычный профиль плюс сведения о том, откуда взято каждое значение. Движок
форматирования о черновике ничего не знает: он получает готовый профиль,
поэтому правила оформления для новой возможности не менялись.

- `sources.py` — чтение методички: Word (python-docx), PDF (pypdf), текст.
  Ошибки объясняются по-русски: скан без текстового слоя, PDF под паролем,
  старый формат `.doc`. Строки PDF склеиваются в абзацы, иначе фразы рвутся
  по ширине страницы.
- `from_text.py` — разбор требований из текста по предложениям. Каждое
  значение несёт цитату-подтверждение. Отдельная тонкость — отрицания:
  во фразе «печатают прописными буквами, полужирным шрифтом, без абзацного
  отступа» слово «без» относится к отступу, поэтому отрицание ищется рядом
  с ключевым словом, а не по всему предложению. Поиск устойчив к искажениям
  PDF: в PDF «ё» может извлечься как латинская буква, а «й» — как «и» с
  мусорным знаком.
- `from_sample.py` — измерение оформления документа: поля, стиль «Обычный»,
  стили заголовков, сноски, таблицы, нумерация страниц, переносы.
- `draft.py` — модель черновика: значения, расхождения, список ненайденного.
  Основа — полный профиль с распространёнными значениями; всё, что не
  подтвердилось методичкой, попадает в список «проверьте» и в ограничения
  профиля.
- `builder.py` — объединение источников (текст важнее оформления), сборка
  профиля, проверка его тем же строгим правилом и запись в личную папку.

Интерфейс: `ui/methodology.py` — кнопка с перетаскиванием и окно проверки
с вкладками «Найденные требования», «Расхождения», «Не найдено».

## Как расширять

**Новый профиль** — файл JSON в `profiles/` или в личной папке. Изменений
в коде не требуется. Формат описан в [PROFILES.md](PROFILES.md).

**Новое правило оформления** — новый модуль в `core/rules/`, функция
`apply_*(context)`, вызов в `core/rules/runner.py` в нужном месте порядка.
Правило обязано:

- записывать изменения в `context.changes` (это отчёт пользователю);
- не трогать текст документа;
- для новых свойств оформления использовать `ensure_ordered_child`
  с таблицей порядка;
- получить тесты: отдельные на само правило и участие в общем контракте.

**Новый элемент документа** — добавить роль в `Role`, признак в
`core/docx/inspection.py` и тест на распознавание, включая случай, когда
приложение обязано отказаться от догадки.

## Тестирование

| Уровень | Что проверяет |
|---|---|
| `tests/unit/` | Проверка профилей, роли абзацев, каждое правило по отдельности, отчёт, подготовка окружения, скрипты запуска |
| `tests/integration/` | Эталонный документ, контракт «меняется только оформление», инспекция, обработка целиком, отчёт, интерфейс |
| `tests/fixtures/rich_docx.py` | Эталонный документ собирается сырым OOXML: сноска, комментарий, объект OLE, элемент управления содержимым, изображение, гиперссылка, поле содержания, разрыв страницы, два раздела, колонтитулы |
| `tests/support.py` | «Измерительный прибор»: разбор пакета, сравнение структуры, сравнение типов содержимого |

Главный тест — `tests/integration/test_apply_contract.py`: он проверяет
утверждение «меняем оформление, а не содержание» на документе со всеми
сложными элементами, и делает это независимым инструментом, а не средствами
самой библиотеки.

Графический интерфейс проверяется в невидимом режиме
(`QT_QPA_PLATFORM=offscreen`), поэтому тесты идут и без экрана.

## Известные ограничения

- Формулы (редактор формул) и встроенные объекты не переоформляются —
  только попадают в отчёт.
- Автоматическое содержание не пересчитывается: поле помечается для обновления.
- Запрет переноса внутри сокращений и чисел Word не поддерживает как
  настройку: включён запрет переноса для слов прописными буквами, остальное
  выводится в отчёт.
- Титульный лист оформляется как основной текст: методичка не задаёт его
  оформление, и приложение об этом сообщает в отчёте.
- Абзацы внутри элементов управления содержимым (готовые блоки Word)
  не попадают в разбор: библиотека не видит их как обычные абзацы.
